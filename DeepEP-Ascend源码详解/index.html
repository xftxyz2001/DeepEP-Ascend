DeepEP Ascend 项目与算子源码详解

DeepEP-Ascend 是面向昇腾 NPU 的通信库。EP 路径把 MoE 路由转换为跨 rank 数据传输、专家连续输入和反向归约；专家 GEMM、激活及路由权重乘法仍由调用方完成。其关键设计是 dispatch 按目标 rank 去重传输、接收端按专家展开；combine 在专家 rank 先做局部归约、源 rank 再归约，以减少同一 token 多次跨网传输。

分析日期：2026-10-14。原始仓库：deepseek-ai/DeepEP-Ascend。固定提交：3b25377d04b24fc6154698ded78a2bcb2c59afff，分析开始时工作区干净，包公开版本为 1.0.0。本说明是该本地版本的静态源码分析，不是 NPU 正确性或性能实测报告。

一次 MoE 数据流

源 rank: x[T,H] + topk_idx[T,K] + 可选 weights[T,K]
   ↓ dispatch_impl：按目标 rank 去重、提交 URMA、复制本地数据
通信窗口：按 source-rank 分区的 token 记录
   ↓ dispatch_copy_epilogue_impl：排空通信、专家展开、padding
专家 rank: recv_x[R_expand,H] + recv_weights[R_expand] + handle
   ↓ 外部专家 GEMM / 激活 / 权重乘法
专家 rank: BF16 expert_output[R_expand,H]
   ↓ combine_impl：同 token 同专家 rank 先归约、回传 partial
源 rank: reduce_buffer[min(P,K),M,record]
   ↓ combine_reduce_epilogue_impl：排空通信、合并 partial 与 bias
源 rank: combined_x[T,H]

最需要记住的接口事实

  1. dispatch(do_expand=True) 是必需条件，默认参数却是 False，照抄默认调用会失败。
  2. combine(topk_weights=...) 不会执行 x * topk_weights；它运输并恢复权重张量。模型应在专家计算侧正确应用一次权重。
  3. .wait() 给当前 stream 建立依赖并执行延迟 epilogue，不等同于 CPU 等待全部设备执行完成。
  4. do_cpu_sync=False 返回的是容量上界张量；真实有效区域由 device counts/metadata 指定，不能把整张量都当有效 token。
  5. 同一 buffer 的通信窗口被 dispatch/combine 复用；必须先完成前一操作的等待与消费，再安全复用。
  6. 当前 EP 路径不经过 aclnnMoeDistributeDispatchV2/V4，也没有 OPP tiling 注册调用链。它直接使用 DeepJIT 实例化设备头文件。
