# 项目介绍与架构

## 定位与功能范围

MoE 的每个源 token 选择 K 个专家，专家分布在 P 个 rank。通信库需要把 token 送到对应专家所在 rank，再把专家输出放回源 rank 的原 token 位置。DeepEP-Ascend 将通信、路由布局变换和归约组合起来，减少由多次普通 collective 加上 permutation 所产生的中间操作。

本版本 README 声明对齐 NVIDIA DeepEP 的 EPBuffer V2.5 风格 API；“API 对齐”不代表所有参数具有相同执行语义。Ascend 实际支持 expanded BF16/FP8 dispatch、BF16 combine、cached handle、专家 padding、确定性排序、延迟 epilogue。源码入口见 [deep_ep/buffers/ep.py:163](../deep_ep/buffers/ep.py)。

| 模块 | Python 入口 | 工作与边界 |
| --- | --- | --- |
| EP | `EPBuffer`、`EPHandle` | MoE dispatch/combine；本文重点 |
| PP | `PPBuffer` | 相邻流水 rank send/recv；实验性 |
| Engram | `EngramBuffer` | NPU BF16/FP8 table，按层 fetch hook；实验性，CPU backing 不支持 |
| Bucket | `BucketBuffer`、`BucketSession` | batch all-gather、注册存储和多组 session；reduce-scatter/all-reduce 尚未实现 |
| 公共管理 | `BufferBase`、`BufferAllocator`、`deep_ep.comm` | 生命周期、容量规划、HCCL handle、barrier 和 stream |
| EPLB | `lb_prefetch_weights`、`lb_reduce_grads` | 保留接口/存储，但 C++ 明确抛未实现错误 |

项目不包含完整专家网络，不负责训练优化器，不提供自动 autograd 集成的完整模型。README 的前向/反向 helper 是如何组合通信原语的示例，不是对任意模型直接可用的训练层。

## 三条不同的数据路径

**数据面**：远端 hidden 和 metadata 通过 URMA SQE 指向的地址传输。dispatch 的 hidden 直接从原始输入 GM 读取，metadata 先打包到独立 GM staging；combine 可直接读单个专家输出或读局部归约后的 send buffer。

**控制面**：计数、前缀和、跨 rank barrier 使用 UBMEM 可达的对称地址及原子操作。这里“对称”表示能够通过本地相对偏移找到远端对应字段，不要求每个进程的虚拟地址数值相同。

**本地整理**：MTE2 将 GM 搬到 UB，标量/SIMT/SIMD 处理布局和归约，MTE3 将 UB 写回 GM。payload 不需要经过 CPU；Host 同步只读取映射 host workspace 内的计数通知。

## AIV 和 Jetty 的组织

设备入口为 `__global__ __vector__`，并调用 `AscendC::InitSocState()`。本版本 EP 使用 AIV，SIMT 负责 routing/索引/SQE 等控制密集工作，SIMD 负责 histogram 和归约，MTE 执行批量搬运。没有在这些 EP kernel 中执行 Cube GEMM。

`num_sms` 在兼容接口中实际表示 AI core 数，Host 乘以运行时 `get_num_vec_cores_per_ai_core()` 得到 AIV 数。不要把它直接当 AIV 数。README 示例 32 AI cores 对应 64 AIV，是该硬件的比例。

通信 context 创建时按运行时总 AIV 数申请 Jetty；EP 启动使用其中与当前 AIV 对应的 Jetty，设备代码把每个 Jetty 作为该 AIV 面向所有远端 peer 的发送队列。它不是“每 peer 每 AIV 一套 Jetty”。见 [csrc/kernels/comm/hccl.hpp:197](../csrc/kernels/comm/hccl.hpp)。

## 与训练和推理的关系

训练、prefill、decode 使用同一个 EPBuffer 接口，没有从接口自动切换到另一套 low-latency API。小 token 数仍可走相同 pipeline，但 launch、barrier、epilogue 的固定成本占比会改变，不能从大 batch 带宽推导 decode 延迟。

局部归约减少跨网传输，但改变 BF16 的归约树；`allow_multiple_reduction=True` 是硬要求。数值验收应使用匹配归约顺序的参考，而不是把不同归约树下逐位相等当作理所当然。
