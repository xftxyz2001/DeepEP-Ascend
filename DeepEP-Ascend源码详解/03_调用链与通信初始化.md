# 调用链与通信初始化

## 导入与构建边界

```text
setup.py
  └─ 编译 csrc/python_api.cpp → deep_ep._C
import deep_ep
  └─ deep_ep/__init__.py:init_jit()
       └─ _C.init_jit(package_root)
            └─ csrc/runtime/jit.hpp:init_jit
                 └─ LazyInit<deep_jit::Runtime<deep_jit::Ascend>>
```

`init_jit` 建立以 EP 为配置前缀、以 package/include 为 include 根的 DeepJIT Config。设备架构、AIV 数、UB 容量由 Runtime 查询；kernel 的 shape、资源数、模式等作为模板参数进入 `std::format` 生成的实例源码。实际 token 数和指针等则作为 launch 实参。

DeepJIT 子模块本地未初始化，因此本次可直接证明的调用链止于 `jit->compile()` 和 `jit->launch()` 的集成层，不声称逐行核验了 DeepJIT 内部 Bisheng 命令、动态加载和底层 runtime launch 实现。README 记录了这些运行时行为。见 [csrc/runtime/jit.hpp:74](../csrc/runtime/jit.hpp)。

## EPBuffer 初始化调用链

```text
Python EPBuffer.__init__
 ├─ get_buffer_size_hint → _C.calculate_ep_buffer_size
 ├─ comm.get_hccl_comm_handle(group)
 │    └─ group._get_backend(npu).get_hccl_comm_name(group.rank())
 └─ _C.EPBuffer(...)
      └─ C++ EPBuffer::EPBuffer
           ├─ comm::Context(...sizeof(EPSignals), buffer+LB...)
           │    └─ HCCLContext
           │         ├─ SymmetricMemory：aclrtMalloc + memset
           │         ├─ HcclCommMemReg
           │         ├─ acquire_ubmem_channels
           │         └─ acquire_jetties
           ├─ set_common_signals：写入 peer 地址表
           └─ aclrtMallocHost + aclrtHostRegister(MAPPED)
Python 构造结束：npu synchronize → dist.barrier → npu synchronize
```

默认借用 torch process group 的 communicator，并缓存 HCCLCommHandle；这与 force_new_comm 的独立 communicator 路径不同。每组内 buffer 编号递增生成注册 UID，因此所有 rank 的构造顺序必须一致。见 [deep_ep/comm/handle.py:33](../deep_ep/comm/handle.py)、[csrc/kernels/comm/hccl.hpp:48](../csrc/kernels/comm/hccl.hpp)。

`SymmetricMemory` 默认使用 `ACL_MEM_MALLOC_HUGE1G_ONLY`，`use_huge1g_page=False` 改为 `ACL_MEM_MALLOC_HUGE_FIRST`；2MiB 是软件 buffer 对齐，不等于底层一定只占用这个粒度的实际页资源。

## UBMEM 与 UBC_CTP 初始化

1. 通过 HCCL rank graph 获取 `layers[1]`，复制 layer 值，避免后续调用使返回数组失效。
2. 对每个非 self peer 找 `COMM_PROTOCOL_UB_MEM` 链接，用 `COMM_ENGINE_AIV` acquire channel；获取远端注册内存，建立 `peer_ptrs`。
3. 再为每个 peer 找 `COMM_PROTOCOL_UBC_CTP` 链接，并要求它们的本地 endpoint 相同。
4. 按 Jetty 数创建 HCOMM endpoint 并注册同一存储；交换独立 listen port，避免默认固定端口冲突。
5. 配置共享发送队列，channel 数为 `max(num_jetties, P-1)`；多出的 channel 用 `rank_idx ^ 1` 配对，解释了多 rank 必须为偶数的限制。
6. 建立供设备读取的 channel/Jetty/peer 元数据查找表。

这些是所选拓扑的资源要求，不能将逻辑返回 `(1,P)` 理解为任意规模、任意物理网络都得到支持。见 [csrc/kernels/comm/hccl.hpp:173](../csrc/kernels/comm/hccl.hpp)、[csrc/kernels/comm/hccl.hpp:197](../csrc/kernels/comm/hccl.hpp)。

## Dispatch 完整链

```text
deep_ep/buffers/ep.py:EPBuffer.dispatch
 ├─ 参数与 cached handle 处理
 └─ self.runtime.dispatch (= _C.EPBuffer.dispatch)
      └─ csrc/buffers/ep.hpp:EPBuffer::dispatch
           ├─ 参数检查、handle 张量和 metadata staging 分配
           ├─ launch_dispatch
           │    ├─ jit->compile("dispatch", 模板实例源码)
           │    └─ jit->launch → dispatch_impl
           └─ epilogue 闭包（立即运行，或登记到 EventOverlap）
                ├─ 可选 Host count wait / 输出容量分配
                ├─ launch_dispatch_copy_epilogue
                │    └─ compile/launch → dispatch_copy_epilogue_impl
                └─ 可选 SF 列主序转换
Python finalize_dispatch
 ├─ 构造 EPHandle
 ├─ 可选 deterministic_sort
 └─ 返回 recv_x / None / weights / handle
```

设备入口和 JIT 模板实参可在 [csrc/kernels/ep/dispatch.hpp:20](../csrc/kernels/ep/dispatch.hpp) 与 [csrc/kernels/ep/dispatch.hpp:84](../csrc/kernels/ep/dispatch.hpp) 对照。`num_hidden_bytes` 区分 BF16/FP8，cached、CPU sync、padding、A、P、E、K、M、AIV 数等会生成不同特化。

## Combine 完整链

```text
EPBuffer.combine
 ├─ 从 handle 取 metadata/topk_idx/psum/M/E/core 数
 └─ C++ EPBuffer::combine
      ├─ BF16/metadata/bias 校验
      ├─ 分配独立 send_buffer
      ├─ launch_combine → JIT → combine_impl
      └─ epilogue 闭包
           ├─ 分配 combined_x[T,H] 与可选 weights[T,K]
           └─ launch_combine_reduce_epilogue
                └─ JIT → combine_reduce_epilogue_impl
```

见 [csrc/buffers/ep.hpp:412](../csrc/buffers/ep.hpp)、[csrc/kernels/ep/combine.hpp:18](../csrc/kernels/ep/combine.hpp)。这里没有 op-plugin 包装、ACLNN GetWorkspaceSize 或 OPP tiling key；Host 层的“选择实例”通过 JIT 模板参数实现。

## 完成语义的四层依赖

| 层次 | 机制 | 保证的范围 |
| --- | --- | --- |
| 核内 | `asc_sync_notify/wait`、ring lock | MTE2/V/S/MTE3 对 UB 和 GM 的先后关系 |
| 本 rank 跨核 | `SyncAll`、inter-arrive/wait | AIV 协同清理、前缀广播、drain 后会合 |
| 网络队列 | SQE/doorbell/CQE、`jetty.drain()` | 等待已提交 URMA 工作的完成通知 |
| 跨 rank | UBMEM barrier signal 原子更新 | 所有 rank 达到约定阶段 |

`comm::scalar::barrier` 在需要 flush/drain 的实例中先等待本地 MTE3，分摊 Jetty drain 到各 AIV，再会合；core 0 向每个 rank 的 signal 做原子加/减并轮询本地目标值，最后按模板选项再会合。两相 signal 与正负交替减少清零竞态。见 [deep_ep/include/deep_ep/comm/barrier.hpp:115](../deep_ep/include/deep_ep/comm/barrier.hpp)。

正常模式 `barrier_in_prologue=False`：issue 负责提交，epilogue 起始处 drain+跨 rank 同步后才读取接收数据。性能测试置 True 时把这段完成等待放到 issue kernel 尾部，epilogue 不重复。**kernel 起始处的基础 barrier 在两种模式中仍存在**；这个开关并非“完全打开/关闭所有 barrier”。

`HcommJetty::ring_doorbell` 写 packed head、执行 DDR DSB、写 doorbell 再 DSB。`drain()` 按 packed head 中的 completion 计数轮询 CQ；检查 owner、status、substatus，然后更新 tail。见 [deep_ep/include/deep_ep/comm/handle.hpp:346](../deep_ep/include/deep_ep/comm/handle.hpp)、[deep_ep/include/deep_ep/comm/handle.hpp:398](../deep_ep/include/deep_ep/comm/handle.hpp)。
