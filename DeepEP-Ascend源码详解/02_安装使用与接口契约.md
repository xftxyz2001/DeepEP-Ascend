# 安装使用与接口契约

## 环境与安装

该提交 README 记录的验证栈是 Linux、Ascend 950DT、CANN 9.2.0、Python 3.12、PyTorch 2.13.0+cpu、torch_npu 2.13.0rc1，以及特定 PoC HDK 配置。这是仓库记录的测试环境，不是本次实测结果；README 的未来固件发布日期计划不作为当前可下载状态的依据。

Host 需要 C++20 与 `std::format`；运行时仍需 Ascend C/Bisheng，因为安装只编译 Host 扩展，设备 kernel 首次使用时 JIT。`setup.py` 链接 `ascendcl/hccl/hcomm/torch_npu`，并有 `aarch64-linux` include 路径，不能直接在当前 Windows 环境构建运行。

在目标 Linux NPU 服务器上，先按现有安装约定 source CANN 环境并安装匹配的 torch/torch_npu，再运行：

```bash
cd /path/to/DeepEP-Ascend
git submodule update --init --recursive third-party/deep_jit
python -m pip install --no-build-isolation .
# 开发时可改用仓库提供的 bash develop.sh
```

`ASCEND_HOME_PATH` 优先，次选 `ASCEND_TOOLKIT_HOME`，`setup.py` 还尝试固定默认路径。构建日志会打印实际 include/library 路径。当前本地 DeepJIT 与 clangd-ascend 子模块均未初始化，固定指针见源码索引；本文没有为分析而修改或初始化原仓库。

多 rank 要求 P 为偶数、所选 netlayer 的所有 peer 有直接 UBMEM 以及 UBC_CTP 链接，并满足单本地 UBC_CTP endpoint 条件。普通 HCCL collective 能运行，不足以证明该路径资源可用。

## 最小 BF16 通信往返

下面是供 Linux `torchrun` 使用的完整示例，展示数据路由与归并，不执行真实专家 FFN。每个 token 选择不重复的专家、权重和为 1，专家操作用恒等映射替代，因此最终结果应近似输入；BF16 权重乘法与两级归约可能引入误差。

```python
import os
import torch
import torch.distributed as dist
import torch_npu
from deep_ep import EPBuffer

local_rank = int(os.environ['LOCAL_RANK'])
torch.npu.set_device(local_rank)
dist.init_process_group(backend='hccl')
group = dist.group.WORLD
P = dist.get_world_size()
T, M, H, K, E = 256, 256, 7168, 2, P * 4
device = torch.device(f'npu:{local_rank}')
x = torch.randn(T, H, dtype=torch.bfloat16, device=device)
idx = torch.topk(torch.rand(T, E, device=device), K, dim=1).indices.contiguous()
w = torch.full((T, K), 1.0 / K, dtype=torch.float32, device=device)
buf = EPBuffer(group, num_max_tokens_per_rank=M, hidden=H, num_topk=K,
               explicitly_destroy=True)
pending = buf.dispatch(x, topk_idx=idx, topk_weights=w, num_experts=E,
                       expert_alignment=128, do_expand=True, do_zero_padding=True,
                       async_with_compute_stream=True, defer_epilogue=True)
rx, _, rw, handle = pending.wait()
# 用恒等专家演示；真实模型在这里执行分组专家计算，并应用一次路由权重。
expert_out = (rx.float() * rw[:, None]).to(torch.bfloat16).contiguous()
y, _ = buf.combine(expert_out, handle=handle,
                   async_with_compute_stream=True, defer_epilogue=True).wait()
torch.npu.synchronize()
print(dist.get_rank(), (y.float() - x.float()).abs().max().item())
buf.destroy()
dist.destroy_process_group()
```

示例启动：`torchrun --standalone --nproc-per-node=8 ep_roundtrip.py`。这采用 torchrun 的常规 rank 语义；不要把它与下文仓库测试自带的 spawn 入口混用。本示例在本次分析中只做语法检查，没有上板执行。

## Dispatch 输入与返回

| 参数或结果 | 形状/类型 | 语义 |
| --- | --- | --- |
| `x` | `[T,H]` BF16 contiguous | 原始 token；T≤M |
| FP8 输入 | `(x_fp8, sf)` | x 为 E4M3FN，sf 为 `[T,S]` 且每元素 2 字节、至少一维 stride 为 1 |
| `topk_idx` | `[T,K]` int64 contiguous | 全局专家编号；`-1` 无选择；有效值应在 `[0,E)` |
| `topk_weights` | `[T,K]` FP32 contiguous 或 None | 伴随路由的数据，不在 dispatch 中乘到 x |
| `num_experts` | E | E 可整除 P，各 rank 连续部署 E/P 个专家 |
| `expert_alignment` | A，2 的幂 | 每专家物理分配长度向 A 对齐 |
| `do_expand` | 必须 True | 一个有效 token/expert 对占一个输出行 |
| `recv_x` | `[R_expand,H]` | 按本 rank 专家连续分段；FP8 时同时返回 scale |
| `recv_topk_idx` | None | expanded 模式不返回展开专家索引张量 |
| `recv_topk_weights` | `[R_expand]` 或 None | 与 expanded 行对应的单个 top-k weight |
| `handle` | EPHandle | 反向路由、计数、cache、确定性排序所需映射 |

非 deferred 返回 `(recv_x, None, recv_weights, handle, event)`；deferred 直接返回 `EventOverlap`，首次 `.wait()` 返回前四项。不要按同一种解包方式处理两者。见 [deep_ep/buffers/ep.py:314](../deep_ep/buffers/ep.py)。

路由应采用正常 top-k 语义，即单 token 的有效专家编号不重复。源码容量上界和 per-expert count 上界依赖此类路由前提；Host 并没有逐元素扫描证明所有编号合法，不应把缺少 Host 报错当作任意路由输入受支持。

## CPU 同步与容量模式

首次调用 `do_cpu_sync=None` 默认 True。epilogue 的 Host 部分轮询映射 host 内存中的 rank/expert count，再按精确的去重接收数和专家对齐总数申请输出。启用 deferred 时，这段 Host 计数等待也推迟到 `.wait()`。

`do_cpu_sync=False` 时，metadata 申请 `P*M` 行，expanded 输出申请：

```text
align(P*M*min(K,E/P) + (A-1)*(E/P), A)
```

这只是上界。真正的去重接收数为 `handle.psum_num_recv_tokens_per_rank[-1]`；有效专家行用 `num_unaligned_recv_tokens_per_expert` 与专家起点确定。未使用的尾部不保证为零；`do_zero_padding` 仅保证各有效专家段的对齐 padding。

## FP8 scale 的含义

设备实现只复制 FP8 字节及 `sf_pack_t=int16_t` 的 scale pack，不在 dispatch 内自动 BF16→FP8 量化，也不在 combine 内反量化。测试 `per_token_cast_to_fp8` 在调用前按 128 个 hidden 元素一组生成 FP32 scale，然后 `.view(torch.int16)`，每个 FP32 scale 占两个 pack。

```python
from deep_ep.utils.math import per_token_cast_to_fp8
xf, scales = per_token_cast_to_fp8(x)
sf = scales.view(torch.int16)
pending = buf.dispatch((xf, sf), topk_idx=idx, topk_weights=w, num_experts=E,
    do_expand=True, do_zero_padding=True,
    async_with_compute_stream=True, defer_epilogue=True)
```

H=7168 时有 56 个 FP32 scale，即 112 个 int16 pack、224B。`use_tma_aligned_col_major_sf=True` 会在 copy epilogue 后执行转置、contiguous、再转置，获得 column-major stride；它不增加 token 维 padding，也不是设备 copy kernel 直接写最终列主序。

## Combine 契约与权重

输入为 expanded BF16 `[R_expand,H]`；handle 必需；可选 `topk_weights` 是 `[R_expand]` FP32。返回 `[T,H]` BF16 与可选 `[T,K]` FP32 weights。普通模式多一个 event，deferred `.wait()` 返回前两项。

可选 bias 为一个或两个 `[T,H]` BF16 contiguous 张量，最终归约加入每个 bias 一次。combine 对 x 只执行加和，不执行乘权，因此真实专家计算必须明确权重应用位置。传回 weights 的能力主要服务反向等场景；最终 weights 通过非重叠槽位的按位 OR 恢复，详见 combine 章节。

## Cached handle 与确定性

```python
cached = buf.dispatch(new_x, handle=handle, topk_weights=new_weights,
    do_expand=True, do_zero_padding=True,
    async_with_compute_stream=True, defer_epilogue=True)
new_rx, _, new_rw, same_handle = cached.wait()
```

cached 模式必须保留 token 数、路由、E、A、M，`topk_idx` 参数需为 None，`do_cpu_sync` 必须 None/False，core 数使用 handle 中记录值。可以更新 x、sf、weights，或省略 weights；不能把新路由与旧 handle 混用。Python 用 `_version` 检测普通 in-place 改动，但 inference tensor、`.data` 和 raw pointer 写入不能可靠检测，因此不可依赖这一检查替代生命周期约束。

`deterministic=True` 在首次 dispatch 后按 expert 和 source-global-token 排序 expanded 输出，并重写 metadata 中的 expanded slots。metadata 行仍保持原去重接收顺序。cached dispatch 已使用重写后的槽位，直接写入确定性布局，不再排序。额外排序和临时张量应计入需要确定性时的开销。

## Stream 与生命周期

EP issue 和 epilogue 都在当前 NPU stream。`previous_event` 被忽略；`allocate_on_comm_stream` 仅兼容参数，不切换分配流；`async_with_compute_stream` 控制事件返回。跨 stream 使用时必须显式建立 producer→consumer 依赖。

`pending.wait()` 先调用底层 event 的 `current_stream_wait()`，然后执行一次 hook。其含义是把后续工作正确排队，不是通用 CPU synchronize；重复 wait 不会再次返回第一次 hook 的结果。非异步返回的 event 内部可为 None，不要无条件调用其 wait。

issue 内核返回后，URMA 可能仍读原 x、metadata_send_buffer 或 combine send_buffer。C++ epilogue 闭包持有这些张量，直到排队通信 drain；调用方仍不能提前原地修改输入或复用通信窗口。必须消费 pending，完成相关流依赖，再 destroy；所有 rank 应以一致顺序构造和销毁 buffer。

训练中 dispatch 的反向使用 combine，combine 的反向使用 cached dispatch，但权重梯度和专家网络反向由模型实现。仓库 helper 不等于已经注册完整 autograd.Function。
